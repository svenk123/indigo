Title: indigo_binarize() overflows a 32-bit int when squaring 16-bit pixel values (MONO16, RGB48), corrupting the threshold

Body:

**File:** `indigo_libs/indigo_raw_utils.c`
**Function:** `indigo_binarize()`
**Affects:** `INDIGO_RAW_MONO16` and `INDIGO_RAW_RGB48` frames (also used internally by `indigo_bahtinov_error()` for the Bahtinov focus estimator)

**Summary**

`indigo_binarize()` computes the mean and standard deviation of the frame to derive a threshold:

```c
uint8_t* indigo_binarize(indigo_raw_type raw_type, const void *data, const int width, const int height, double sigma) {
	int size = width * height;
	long sum = 0;
	long sum_sq = 0;
	switch (raw_type) {
		...
		case INDIGO_RAW_MONO16: {
			uint16_t *source_pixels = (uint16_t *)data;
			for (int i = 0; i < size; i++) {
				int value = source_pixels[i];
				sum += value;
				sum_sq += value * value;
			}
			break;
		}
		...
	}
	double mean = (double)sum / size;
	double stddev = sqrt((double)sum_sq / size - mean * mean);
	int threshold = mean + (sigma * stddev);
```

`value` is declared as `int`, and `value * value` is therefore evaluated in **32-bit** arithmetic before being added to the 64-bit `sum_sq`. For a 16-bit pixel value above 46340, `value * value` already exceeds `INT32_MAX` (`65535² ≈ 4.3×10⁹` vs. `INT32_MAX ≈ 2.1×10⁹`), so the multiplication overflows (undefined behaviour in C; in practice wraps to a negative 32-bit value on common platforms/compilers) before it is widened and added to `sum_sq`. The same pattern is used for `INDIGO_RAW_RGB48`.

**Impact**

This corrupts `stddev` and therefore `threshold` for **any real 16-bit image that contains bright pixels** (stars, saturated regions, hot pixels) - not an edge case for astronomical images. Since `indigo_binarize()` is also called from `indigo_bahtinov_error()`, this can make the Bahtinov focus estimator pick a wrong threshold and reject or mis-detect the diffraction spikes on frames with a bright enough star or an over-exposed area.

**Suggested fix**

Widen `value` to a 64-bit type before squaring, e.g.:

```c
sum_sq += (long)value * value;
```

(equivalently `(int64_t)value * value`). This is a minimal, behaviour-preserving fix for images that did not previously trigger the overflow, and a correctness fix for the ones that did.

**How to reproduce**

Call `indigo_binarize(INDIGO_RAW_MONO16, data, width, height, sigma)` on a 16-bit frame containing pixels with value > 46340 (e.g. a background of a few hundred counts plus a handful of saturated 65535 pixels). Compare `stddev` against a reference computed with 64-bit squaring (e.g. in Python/`numpy`) - they diverge as soon as enough bright pixels are present to push `sum_sq` past where the per-pixel 32-bit overflow changes the accumulated 64-bit total.
