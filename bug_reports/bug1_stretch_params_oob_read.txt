Title: indigo_compute_stretch_params() reads past the end of the frame buffer for Bayer planes with a row/column offset

Body:

**File:** `indigo_libs/indigo_stretch.cpp`
**Affects:** `indigo_compute_stretch_params_8_rggb/gbrg/grbg/bggr` and the corresponding `_16_*` functions (used by `indigo_raw_to_jpeg()` for every colour-camera preview)

**Summary**

For a Bayer frame, `indigo_compute_stretch_params()` is called once per colour plane. The R, G and B planes start at different offsets into the buffer depending on the Bayer pattern - `buffer`, `buffer + 1`, `buffer + width` or `buffer + width + 1` - but every call passes the *same* `width` and `height` as the full frame:

```c
extern "C" void indigo_compute_stretch_params_16_rggb(const uint16_t *buffer, int width, int height, int sample_by, double *shadows, double *midtones, double *highlights, unsigned long **histogram, unsigned long *totals, float B, float C) {
	indigo_compute_stretch_params(buffer, width, height, sample_by * 2, 2, &shadows[0], &midtones[0], &highlights[0], histogram[0] = (unsigned long *)indigo_safe_malloc(sizeof(unsigned long) * 256), &totals[0], B, C);
	indigo_compute_stretch_params(buffer + 1, width, height, sample_by * 2, 2, &shadows[1], &midtones[1], &highlights[1], histogram[1] = (unsigned long *)indigo_safe_malloc(sizeof(unsigned long) * 256), &totals[1], B, C);
	indigo_compute_stretch_params(buffer + width + 1, width, height, sample_by * 2, 2, &shadows[2], &midtones[2], &highlights[2], histogram[2] = (unsigned long *)indigo_safe_malloc(sizeof(unsigned long) * 256), &totals[2], B, C);
}
```

Inside `indigo_compute_stretch_params()`, the sampling loop iterates `line_index` up to `height` (not `height` minus the plane's row offset):

```c
} else {
	const T *line = buffer;
	for (int line_index = 0; line_index < height; line_index += sample_rows_by) {
		for (int column_index = 0; column_index < width; column_index += sample_columns_by) {
			T value = line[column_index];
			...
		}
		line += width * sample_rows_by;
	}
}
```

For the G plane (`buffer + 1`) and B plane (`buffer + width + 1`), this walks `line` one row further than the actual plane extends. For an *odd* frame height this reads up to `width` values past the end of the allocated buffer; for certain frame widths it also silently reads into whatever follows the buffer in memory instead of raising an error. The column-offset planes (`buffer + 1`) have an analogous off-by-one at the right edge.

**Impact**

- Out-of-bounds heap read, reproducible as a crash if the buffer ends near an unmapped page (e.g. right after an `mmap`-based allocation with a guard page).
- For frames where this doesn't crash, the median/MAD used to compute the preview stretch parameters is silently computed from a few stray values that don't belong to the image, which can affect the preview appearance.
- Hit on every JPEG preview of a colour camera image with the affected Bayer pattern and an odd height (or matching width), i.e. a common, not a rare, case.

**Suggested fix**

Give `indigo_compute_stretch_params()` the actual origin (`column_offset`, `row_offset`) of the plane instead of only a pointer, and bound the sampling loop to `width - column_offset` columns and `height - row_offset` rows, e.g.:

```c
const int columns = width - column_offset;
const int rows = height - row_offset;
...
for (int line_index = 0; line_index < rows; line_index += sample_rows_by) {
	for (int column_index = 0; column_index < columns; column_index += sample_columns_by) {
```

Note this is a genuine behaviour change for odd heights / certain widths: the stretch parameters will differ slightly from the current (out-of-bounds-influenced) result for those specific sizes, because memory beyond the frame no longer contributes to the median. All other frame sizes are unaffected.

**How to reproduce**

Allocate the input buffer so that it ends exactly on a page boundary followed by an unmapped (`PROT_NONE`) page (e.g. via `mmap`), fill it with a normal Bayer test image of odd height, and call e.g. `indigo_compute_stretch_params_16_gbrg()` or `indigo_compute_stretch_params_16_bggr()` on it - it segfaults. With a regular `malloc()`, the read still happens but usually lands in adjacent heap memory instead of crashing, so it is easy to miss without a guard page.
